1. The Core Engineering Question: Can We Just Use 2x Tesla P40s?

Why You Don't Actually Need the RTX 3060 for MoE Decode Speed

Many engineers assume that modern Tensor Cores are mandatory to make MoE fast. But local LLM generation splits into two completely separate mathematical phases:

  1. Token Generation (Decode Phase) is 100% Memory Bandwidth Bound:
    When generating 1 token at a time for a single user, the arithmetic intensity is tiny. The GPU is NOT compute-limited; it is waiting for memory. In Mixtral 8x7B, each token requires streaming ~7.1 GB of active weights.
    • Tesla P40 has a 384-bit memory bus delivering 345.6 GB/s.
    • RTX 3060 has a 192-bit memory bus delivering 360.0 GB/s.
    Because the P40's bus is twice as wide, it streams weights at virtually the exact same speed as an RTX 3060! During token decoding, the Tesla P40 does not bottleneck generation speed at all. Both cards decode Mixtral at 22 - 27 tokens/second.
  2. Where Tensor Cores Actually Matter: Prompt Ingestion (Prefill):

Adding the RTX 3060 only made prompt processing faster on its assigned 11 layers, but because execution pipelined through the P40's 21 layers anyway, overall prompt ingestion was still largely paced by the P40!

3. Deep Dive: How the Pascal Shader Workaround Functions

The Pascal Architecture Problem (The FP16 Flaw)

In 2016, NVIDIA released the Pascal generation. While the enterprise GP100 die (Tesla P100) received full-speed FP16 compute, NVIDIA deliberately crippled half-precision (FP16) compute on the GP102 die (Tesla P40, GTX 1080 Ti, Titan Xp) to prevent cannibalization of high-margin datacenter cards.

  • Pascal GP102 FP16 Rate: Runs at an abysmal 1:64 rate of FP32 (only ~0.18 TFLOPS!).
  • The Default Failure (Without Fixes): Standard modern AI frameworks (PyTorch, vLLM, HuggingFace) assume modern GPUs have fast FP16/BF16 Tensor Cores. If you run naive FP16 code on a P40, prompt prefill slows to a crawl (literally ~0.5 to 2 tokens/sec, taking 15 to 40 minutes for a 2k prompt).
Prefill Speed: Before vs. After the llama.cpp Pascal Fix:
The prefill figures in this report (~45 - 65 tok/s for dual P40s on Mixtral 8x7B) already incorporate all of the llama.cpp shader optimizations:
  • Without Fixes (Naive FP16 GEMM): ~0.5 - 2 tok/s → Wait time for 2k prompt: 20 - 45 minutes (completely unusable).
  • With llama.cpp Fixes (FP32 + DP4A INT8): ~45 - 65 tok/s → Wait time for 2k prompt: ~35 - 40 seconds (a massive ~30x to 50x speedup!).
The remaining gap between the P40 (~55 tok/s) and an RTX 3060 (~300+ tok/s) in prefill is purely physical: the RTX 3060 possesses dedicated Ampere Tensor Cores, whereas the P40 must compute dense matrix multiplies on its standard shader ALUs.

The Engineering Workaround in llama.cpp / GGUF

The developer community around llama.cpp developed specialized CUDA kernels that bypass this hardware limitation entirely:

  1. Direct FP32 Register Dequantization: Instead of dequantizing GGUF weights (Q4_K, Q5_K, Q8_0) into FP16 arrays in VRAM, llama.cpp's specialized CUDA kernels dequantize directly into 32-bit single-precision floating point (FP32) CPU/GPU registers on the fly. The P40 delivers ~12 TFLOPS of FP32 throughput, which is plenty of compute for single-user token decoding!
  2. Native INT8 Hardware Dot-Product (__dp4a): Pascal GP102 natively includes hardware instructions for __dp4a (which computes the dot product of four 8-bit integers and accumulates into a 32-bit integer in a single clock cycle). In llama.cpp, quantized GEMM/GEMV operations compiled for Compute Capability 6.1 (sm_61) utilize DP4A to achieve up to ~47 INT8 TOPS!
  3. FlashAttention Replacement (Tiled / Chunked SDPA): Modern FlashAttention-2 relies strictly on Ampere/Hopper Tensor Cores (`sm_80+`). When running on Pascal, llama.cpp falls back to an optimized tiled Scaled Dot-Product Attention (SDPA) computed in FP32. To prevent memory bandwidth saturation during prefill, passing -b 512 -ub 256 (micro-batch size 256) keeps intermediate attention matrices inside the GPU's L2 cache.

6. The 4 Critical Engineering Constraints of Running 2x P40

1. Zero Display Outputs (Headless Server Cards)

Neither Tesla P40 has an HDMI or DisplayPort output.

  • If your CPU has an integrated GPU (iGPU): (e.g. Intel non-F CPUs like i5-12600K/13600K, or AMD Ryzen 7000/8000/9000), you simply plug your monitor into the motherboard HDMI port! Linux handles desktop display via iGPU while directing AI workloads to the dual P40s.
  • If your CPU has NO iGPU: (e.g. Ryzen 5600X, 5700X, 5800X, or Intel "F" series), you MUST add a cheap, low-power display card (like an old $25 GT 710 or GT 1030 in an open PCIe x1 slot) to drive your monitors.

2. Heavy Power Draw: 850W PSU Minimum

Each Tesla P40 has a 250W TDP:

  • Dual P40 Peak Draw: 250W + 250W = 500W TDP purely for GPUs under full compute load.
  • Total System Power: Combined with CPU and motherboard (~150W), full system draw reaches ~650W.
  • PSU Requirement: A high-quality 850W 80+ Gold power supply with four independent 8-pin PCIe leads is strictly required. (Setup A only needed 750W; Setup B only needed 650W).

3. Motherboard Slot Spacing & Blower Dimensions

Each P40 is a dual-slot card that extends rearward with the 9733 turbine blower fan attached:

  • Total Card Length: 267mm card + ~55mm blower shroud = ~322mm total length. Ensure your PC chassis has at least 330mm GPU clearance.
  • PCIe Slot Spacing: You need an ATX motherboard with at least 3 to 4 slots of spacing between the first and second physical PCIe x16 slots. If the two slots are adjacent (2-slot spacing), the second card will choke the blower air intake of the first card.

4. "Above 4G Decoding" in Motherboard BIOS

Addressing 48GB of VRAM across two cards:

  • In your motherboard BIOS, you MUST enable "Above 4G Decoding" and "Resizable BAR / 64-bit BAR Support".
  • Without Above 4G Decoding enabled, the system memory mapper will fail to allocate the 48GB PCIe BAR space, and the system will throw Code 43 or fail to POST. Modern AM4/AM5 and Intel LGA1200/1700 boards support this out of the box.
  • OS: Linux (Ubuntu 22.04/24.04) is mandatory. Driver 535.xx or 550.xx runs dual P40s in TCC compute mode flawlessly.
